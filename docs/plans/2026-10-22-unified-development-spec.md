# YGO-Kito 统一开发说明与训练交付计划

版本：1.1 设计整合稿｜日期：2026-10-22（UTC+8）

**状态：整合已确认的设计，不代表代码已开发、兼容已验证、训练已启动或指标已达标。** 本文将 2026-10-21 至 22 日逐项讨论接入《游戏王AI项目设计定稿.docx》1.0（2026-10-19）。本文明确更新的部分优先；未更新的产品意图和约束继续继承原定稿。11 份归档原件及其清单保持不变。

## 1. 目标、范围与执行边界

核心是自行训练的决斗与构筑模型组，形成对合理构筑、废件、上限件、牌效、妥协等情境概念的判断能力，并能迁移到其他卡组。珠泪哀歌是复杂、随机性强的起步课程，不是永久能力边界。100 小时内获得优秀基础能力是目标，不能保证“几乎完全理解”，也不能以只会几套牌替代目标。

- 开发：云端 Codex；训练：腾讯云；训练后：本地 PC 推理与低资源持续微调。
- 当前纳入 PC，**手机端、YGOMobile 对接与手机硬件验收暂移出本期规划**，原因是没有合适测试机；将来另行恢复，而非永久取消。
- 第一阶段使用真实规则核心，不要求完成现有图形客户端接入；第二阶段训练前，必须通过电脑端 YGOPro／萌卡兼容门槛。批量训练可以 headless，不逐局渲染 GUI。
- LLM 不是基础模型组必需品；先跑通基本模型组和训练链路，再用于检索、辅助、抽查、训练催化或补充对手。
- **LoRA 是后续持续适配的常规路线，不再与 LLM 一并写成“完全可不开展”。** 基模先训练，接口先预留；环境、禁限表、卡组迭代按需要微调，不为每个卡组重新训练一套完整基模。
- 本文仅授权范围内的文档整合，不自动启动开发、租用算力、付费 API、安装或训练。约 100h 上限不是消费授权。
- 本次远端文档更新不表示离线电脑 N:\YGO-Kito 已同步。

## 2. 模型组与职责

### 2.1 结构

| 组成 | 主要职责 | 计算取向 | 首版实现方向 |
| --- | --- | --- | --- |
| 决斗模型 | 从合法选项作出正确动作，兼顾资源、恢复与妥协 | 相对短、快速的推理，优先正确率和时延 | 独立轻量 Transformer、历史记忆、动作排序/策略与价值估计 |
| 构筑·目标子模型 | 实现用户目标、提出组合及可执行路线 | 更深候选探索与验证 | 独立小型 Transformer；可配搜索与规则验证 |
| 构筑·优化子模型 | 在保留目标基础上改善稳定性、废件负担、抗打断、续航、环境适应 | 更长迭代，允许慢于决斗 | 独立小型 Transformer；编辑、比较与实战纠偏 |
| 统筹模型 | 包裹模型组，统一任务入口、模型调度、预算和结果托付，对接 LLM/agent | 轻量，避免成为实时瓶颈 | 小型可学习调度器＋确定性程序控制；首阶段规则调度并记录日志 |

三个执行模型先独立训练编码器与权重，共享卡片、标签和接口规范；不强制共享可训练权重，也不承诺全组端到端联合训练。统筹模型的具体网络尚待实测选择，不新增一个通用大语言模型。

“短/长推理”指搜索深度、候选数、迭代和计算预算，不以解释文字长度代替，更不要求输出长篇思维文本。统筹分配任务后，决斗实时内循环直接连接规则引擎和决斗模型，不为每次点击额外往返统筹/LLM。

### 2.2 目标与优化的边界

目标子模型可以暂不追求构筑合理性，但**仍须满足卡池、禁限表、张数、固定卡要求及真实起始条件等硬约束**；不能靠非法路线完成目标。输出包括候选构筑/组合、起始条件、合法路线、随机依赖与未满足项。

优化子模型可替换单卡或整个小轴，兼顾启动率、废件率、抗打断、资源循环和环境表现；不能偷偷删掉用户目标。确须妥协时显式给出取舍，按允许范围优化。成功展开一次不等于稳定实现。

构筑内循环固定为：**目标 → 改进 → 目标 → 改进**。支持从零生成和已有卡组修改。纯轴、混轴均可，不为了展示能力强制混轴。

### 2.3 统筹与外部接口

程序负责状态、权限、超时、规则校验、版本、资源限制和错误处理；学习调度器负责何时调用哪个模型、是否继续优化、如何分配预算。第一阶段规则调度即可建立可复现日志；后续再训练轻量调度能力，不挤占主要训练目标。

接口先提供 CLI 与本地结构化服务，稳定后供 PC 应用与外部 agent 接入。LLM 断开后基础决斗、构筑和评测仍须工作。正式产品的实际对局和随机对手路径保留本地运行原则；外部 API 主要用于构筑辅助、检索、评估和复盘，开发训练中的 API 对手是明确隔离的补充路径。

## 3. 数据、标签与规则原意

### 3.1 统一数据底座

- 卡片表示三层：基础属性、效果结构、情境关系；稳定卡片 ID、别名及中日英名称对齐，保留中文效果和日文裁定依据。
- 禁限表与卡池发行截止日分开；默认已发行卡，允许明确的历史或自定义卡池，不把月份当作卡池。
- 标签联合连接符统一为 **·**。保存主体、来源/去向、是谁的卡、条件、费用、时点、对象、自肃及上下文。
- 原始卡效/规则事实、模型推断、LLM 审核意见和人工修正分层记录，不让推断覆盖事实。
- SQLite 管理卡片、标签、卡组、版本和实验索引；大批轨迹另用分片文件，具体格式通过吞吐测试确定。

### 3.2 标签驱动构筑不被模型化改写

保留原定稿的**效果、主题、情境角色交叉检索**，不是依次硬过滤：先用标签缩小候选，再读取实际效果与条件，验证合法路线。上下文区分必要废件、半废件、当前不可用、低收益和暂未知用途，不机械删除所有“废件”。“额外泛用”指额外卡组泛用卡，不是更多主卡组泛用。

完整循环：目标/主题/CB 约束 → 交叉检索 → 读取效果 → 核心与额外组合 → 规则验证 → 启动、废件、自肃和抗打断分析 → **按缺口再次检索、扩大候选池** → 优化与重验。不能把第一次召回结果封闭成永久候选池。保留失败原因，区分检索、排序、规则验证和实战评价。

换备方案需要明确换入、换出及换备后功能完整性。保留从单轴到双轴、复杂混轴的递进能力目标及用户亲手学习 Python 的原有材料。

### 3.3 标签审核

先自动处理；接入 LLM 后可联网检索抽样判断训练结果。难评样本去重分类，每批最多转交 **3 个典型**人工纠正。没有证据的未知信息不得猜成监督标签；本流程不成为基础训练的必需前置。

## 4. 合法可见信息、动作与搜索

- 决斗策略只读取正常玩家合法可见信息：己方手牌、公开场面、已公开历史。不能读取对方真实暗牌、牌组顺序或未来抽牌。
- 对未知信息可推测和记忆，必须区分已知与概率估计；首版不要求独立猜手模型。
- 搜索未知状态只能从合法信息构造可能状态，不能用引擎真实隐藏状态当答案。完整调试日志与策略输入隔离。
- 引擎给出合法动作及参数，模型选择发动、对象、素材、顺序、数量或通过；复杂选择分步执行并保持计划。LLM 对手遵守相同观察与动作边界。
- 先建立无搜索基线，关键分支按需搜索，比较质量与时间收益；考虑随机结果和对手响应，不能把理想展开当必然。
- 搜索预算耗尽时返回当前最佳合法动作；真正比赛超时由独立计时控制器认输处理，两者不能混为一谈。
- 保留原定稿运行目标：PC 决斗端到端约 **1–3 秒/动作**，构筑 **3–30 分钟**内返回最佳已验证候选及未满足项。尚无性能实测。

## 5. 模型间交接与反馈

建议接口契约至少包括：任务/运行 ID、模型及 LoRA 版本、规则核心/卡池/禁限表版本、目标与硬约束、合法观察、动作或构筑候选、验证状态、置信/不确定性、预算与错误原因。具体字段和序列化在第一阶段定稿，不将此建议字段表误称已实现 API。

- 目标模型交付目标路线，优化模型交付合理性改善与保留目标证据，统筹接收可用构筑并分配决斗验证。
- 目标路线无效返回目标模型；合法但不稳定返回优化模型；操作失误返回决斗训练。允许联合诊断和不确定结论，不将所有输局归为构筑失败。
- 最终胜负是决斗训练的主要信号，目标终场、有效妥协和资源利用为辅助；不直接奖励纯展开长度或怪物数量。
- 低收益迭代或预算结束，交回最佳已验证版本与未解决问题，不无限循环。

### 5.1 预测胜率与百场/千场反馈

构筑模型把构筑托付统筹；**统筹或构筑模型**预测该卡组在指定环境的平均胜率。预测须在验证前登记，绑定构筑、决斗策略、对手分布、先后手、环境与 BO1/BO3 口径。

用户规则保持原意：

1. **百场内**实际胜率明显低于预测，提示构筑模型重新评估。
2. **千场内**仍明显低于预测，强制进入重新构筑流程。
3. 不能误写为“仅在第 100、1000 场整点检查”。需预设检查点或持续监控方法，并控制重复观察的统计误报。
4. “明显”需结合预设差值与不确定性；具体差值、场次单位、平局统计、检查频率和序贯判定方法仍待实施前冻结。
5. 保留预测与版本谱系，不得靠下调预测或任意重置计数清除预警。更改环境或驱动版本时单独分层比较。
6. 排查操作、环境和系统异常，但不绕过用户要求的强制重构流程；重构可以保留有效核心，并非必然整套推翻。
7. 新候选重新验证后才晋升；不要求所有候选交付前先打满千场。

## 6. 训练路线与数据来源

### 6.1 分开起步，交替协同

- 决斗以 PPO 为首版强化学习基线，使用合格 bot、历史快照和自博弈；可用引擎验证的 bot/搜索轨迹进行模仿热身。
- PPO 为 on-policy 路线；历史轨迹不能直接混入当前 PPO 更新。旧环境复习应由当前策略重新采样，或使用分离的监督/蒸馏目标。
- 目标子模型从候选搜索与引擎验证路线学习；区分非法、明确路线失败和预算内未找到，不把“未找到”标成“不可能”。
- 优化子模型学习构筑比较和修改，固定决斗驱动版本、对手池、评估预算；实际对局校正代理评分。
- 交替过程：固定决斗策略评构筑 → 筛选多样候选并改进构筑 → 训练决斗策略 → 冻结新驱动并统一重评。避免把驾驶水平提升误判为构筑提升。
- 调度模型先积累规则调度日志，后续学习质量/成本分配，不要求所有模型同步端到端训练。

### 6.2 可用数据与隔离

用户能提供可靠构筑，大规模机读历史对局已经遗失。可靠牌表不等于动作监督。主要由引擎对局、搜索、自博弈生成轨迹；平台录像用于少量关键局面校对，不以大规模 OCR/视频恢复作为前置。

按完整对局划分训练、验证、独立终验；保留未训练的构筑变体、策略和随机种子。固定历史策略快照并复习旧环境，防止遗忘。每条数据带时期、规则、卡池、牌表、双方驱动和可见边界版本，避免跨期非法混用。

## 7. 珠泪哀歌三时期课程

| 时期 | 卡池边界 | 构筑答案与课程 |
| --- | --- | --- |
| 2022 年 7 月表 | 截至 2022-09-30 已发行 OCG 卡 | 可靠参考/推荐构筑学基础；先主要同期其他卡组，少量强参考珠泪内战，逐步增加内战 |
| 2022 年 10 月表 | 截至 2022-12-31 已发行 OCG 卡 | 可靠参考/推荐构筑学基础；具体对手名单、比例和递进安排尚未单独冻结 |
| 2026 年 10 月表 | 数据准备时选定具体日期并冻结 | 继承前两期权重，不直接给主构筑模型现成目标答案；先各类混轴珠泪，再增加主流外战 |

前两期参考不是数学上唯一最优。第三期“从零”指从目标自主构筑，不是随机初始化权重，也不因无直接答案就称无监督学习。训练期间不自动纳入新卡。

2022 年 7 月雷精、烙印、白银城、黄金国，以及 2026 年荷鲁斯珠泪、巳剑珠泪、堆墓均，是用户提供的候选；热度和具体牌表合法性须核验，不能写成已冻结对手池。

用户允许第三期现成混轴珠泪作对手，主模型会获得间接示范，不能宣传完全无示范；不把这些牌表直接作为主构筑模型答案。主流可使用成熟构筑；非主流/娱乐对手可由辅助策略、历史快照或后置 LLM 操控。精确对手比例、升级阈值及辅助模型实现待实测确定。

## 8. 对手数量与 DSH 接入

既有机器人需按“**具体时期 × 固定牌表 × 驱动版本**”检查合法性和基本操作。同名主题或能启动不等于符合该期、具备足够强度。

最新方向是优先评估复用现成 DSH 通用桥接，补充机器人不足，避免为每个牌组新写策略。仍保留新写与跨期改造的成本比较作为回退准则；不重写规则引擎。

此前只读研究找到 `mellfy-puppy/ygo-tools-for-dsh`，路径涉及 DSH、AI.Server、WindBot 与 YGOPro2 房间，可通过观察/动作工具连接模型。它明确出现 YGOPro2，**不能据此宣称已兼容全部 YGOPro／萌卡**。provider 可接不同模型不等于每种 GPT/DeepSeek 已验证会正确且高效打牌；`learnDeck` 经验文本不是模型权重训练。

LLM 对手采用异步、封顶预算与降级策略，不让 API 延迟阻塞主训练。强度、时延、令牌费用和兼容版本均需 CPU/低成本试验。其轨迹可作为合法边界下的辅助数据，不伪装成当前 PPO on-policy 数据。基础训练不得因未连接 LLM 无法运行。

## 9. LoRA 生命周期

1. 先形成可迁移基模；预留可适配层和保存/加载接口。
2. 新卡先更新数据、标签、规则与回归集，不自动每张卡都训练。
3. 按禁限表、环境或牌组任务建立有版本、可回退的 LoRA，有限预算微调并比较未微调基线。
4. 检验新任务收益、旧任务退化、资源与时延，合格后才发布；不假设无限叠加适配器仍有效。
5. 合并、组合、路由或恢复基模全量训练均需单独验证；目标层、秩、精度和量化不是本次既定数值。
6. 本地真实/人机对局持续回流，在合法信息与训练/验收隔离下周期微调，不将在线每局即时更新设为强制。

## 10. 分阶段工作与退出条件

下列为已确认方向的工程拆解；具体文件布局、测试框架及实现参数由开发时落实。

| 阶段 | 工作与交付 | 退出条件 |
| --- | --- | --- |
| 0：资料与契约 | 继承原定稿；记录决策、待测项、规则/数据/接口规范 | 范围清晰，原件无改写，版本优先级明确 |
| 1A：真实规则与数据 | 冻结兼容 core/scripts/cards.cdb/协议/禁限及哈希；合法观察与动作；headless 对局和回放；三期数据与标签 | 完整对局可复现，无隐藏信息泄漏，规则/卡池检查与数据隔离通过 |
| 1B：模型与 CPU 管线 | 三执行模型及统筹接口；训练/评测/断点恢复；版本日志；LoRA 接口；bot/DSH 适配小试；硬件采集 | 各模型前向/损失/恢复可测试，不能遗漏构筑；有基础合法对手且外部 API 不成为硬依赖 |
| 训练前 PC 门槛 | YGOPro／萌卡实际分支动作、连锁、回放一致性；锁定兼容组合 | 门槛通过才能转入付费训练；仅 headless 自测不替代此项 |
| 2A：吞吐与小训练 | 测真实对局/样本吞吐、显存、时延、训练信号与恢复 | 能估算剩余预算及样本规模；不可行先诊断，不按日历硬进入下一期 |
| 2B：三个时期 | 按课程分开起步、交替训练决斗/目标/优化，并逐步调度学习 | 每期冻结模型、数据、对手与评估记录，记录未达项和转移依据 |
| 2C：迁移与终验 | 陌生卡组 LoRA；独立 BO3、概念、资源、恢复评测 | 可复现结果，明确达标/未达标/证据不足，而非仅“能运行” |
| 3：本地 PC 与应用准备 | 本地加载、低资源继续训练接口、资源报告、CLI/服务；再决定 PC UI 与导出 | 有目标 PC 实测和接口稳定证据，应用开发不冒充训练完成 |

CPU 可完成的依赖、数据、兼容检查尽量在计费 GPU 前完成；不能假定云 Codex 提供无限免费 CPU。原 Python 亲手练习材料保留，不由此次统一文档替用户完成所有学习任务。

## 11. 100 小时预算与止损

**约 100 小时是总上限而非必须用满。** 预算核算默认按单卡累计实例小时；若采购多卡或不同计费模式，须在开机前明确等价预算，不可将多卡 100 墙钟小时默认视为同一额度。安装、下载、空转、失败、GPU 教师推理和评测均纳入，不按利用率打折。实际金额还取决于机型、CPU/存储等计费，采购须另获执行授权。外部 LLM API 费用单独封顶。

| 用途 | 初始小时分配 |
| --- | ---: |
| 吞吐检查与小规模训练 | 5 |
| 2022 年 7 月环境 | 25 |
| 2022 年 10 月环境 | 25 |
| 2026 年 10 月环境 | 20 |
| 陌生卡组 LoRA 迁移与正式验收 | 10 |
| 故障、重训、复验预留 | 15 |
| 合计 | 100 |

这是一套可按首 5 小时实测修订的初始分配，不是每到时点自动晋级。每期额度覆盖决斗、两个构筑子模型、采样、评估和必要轻量统筹训练，不额外悄悄加预算。迁移和 BO3 终验的 10h 是否足够尚未证实，必要调整须说明收益和对预留的影响。

- 无学习信号先查表示、奖励、数据与驱动，不盲目烧完额度；连续无改善的具体门槛在训练前定。
- checkpoint 保存全模型、LoRA、优化器、调度器、RNG、数据游标、依赖与数据版本、累计计费预算，并实际验证恢复。
- 到上限保存最佳版本、未达项和下一步，不自动续费。实例退出训练不代表停止计费，必须确认实际停机状态。
- 旧固定 6h LoRA 配额已撤回；这里的 10h 是迁移与验收联合预算，不恢复旧建议。

## 12. 验收：强度、泛化与统计

### 12.1 正式对局

训练主要 BO1；正式验收以含换备的 **BO3 大局胜率**为准。冻结独立参考对手、牌表及驱动，不以同模型自博弈天然 50% 或单弱 bot 胜率代替通用能力。

| 环境 | 外战目标 | 强参考珠泪内战目标 |
| --- | --- | --- |
| 2022 年 7 月 | ≥60% | 接近 50% |
| 2022 年 10 月 | ≥60% | 接近 50% |
| 2026 年 10 月 | 阶段目标 30–40% | 阶段目标 30–40% |

超过 2026 目标上界是更好，不是失败。上述是用户目标，不是已测成绩，也不把用户对历史环境优势/劣势的判断当已核事实。

每期初始至少 **200 场外战 BO3＋200 场内战 BO3**，报告 95% 置信区间、先后手和对手分项；边界或区间过宽补样本，预算不足标“证据不足”。“接近”的容差、区间用于通过判定的方法、平局口径及多次观察规则须在正式验收前冻结，不能只见点估计过线即宣称成功。失败、超时、崩溃均保留分类与总体计数，不剔除坏样本美化胜率。

### 12.2 构筑与概念

- 目标模型：合法性、目标达成、真实起始条件、随机依赖及失败类型。
- 优化模型：保留目标的同时改善启动、废件、抗打断、资源与独立对局表现，不能只用自己输出的分数验收。
- 概念：用不同局面和构筑比较检验合理构筑、必要废件/上限件、牌效与妥协；不能只凭一套珠泪胜率宣称理解。
- 跨牌组：至少 2 套未用于专门训练、机制有差异的卡组，有限且公平的微调预算，对比珠泪基模＋LoRA 与同结构随机初始化基线的学习速度、操作和构筑改善。曾作为对手间接出现须披露，不能称完全没见过。
- 泛化验收不是简单证明 LoRA 文件能加载；若预算下对照不充分，报告不充分而非补写成功。

### 12.3 运行与可复现性

PC 决斗端到端报告中位数、P95/P99、超时率，目标 1–3 秒不能仅测神经网络前向。构筑目标 3–30 分钟，输出最佳合法候选与未满足项。保存规则、随机种子、日志和可成功回放的样本，区分本地运行、API 辅助与搜索模式结果。

## 13. 硬件压力必须同步收集

区分云端训练、PC 推理和 PC 微调；分别给各模型与全流程数据：CPU 利用率、RAM 峰值、GPU 利用率/显存峰值、加载时间、端到端时延、吞吐、磁盘空间及读写；可获得时记录功耗、温度和降频。

每条报告绑定硬件、驱动、模型/LoRA 版本、精度、并发、搜索预算和任务规模。交付原始采样日志、汇总表及可复现采集脚本；压缩和低资源方案必须同时报告质量变化。当前未进行这些实测。

本期不采手机实机数据，不因移除手机而取消 PC 监测。本项目尚未冻结统一占用百分比上限，资源阈值依据 PC 测试确定。

## 14. 工程选型与尚未冻结项

已确认基线：Python＋PyTorch，三个独立执行模型与轻量统筹，真实规则引擎，结构化动作/观察、SQLite 索引＋轨迹分片、LoRA 生命周期、CLI/本地服务先行。目标对接 PC YGOPro／萌卡，EDOPro 仅参考。

实施前/小试后须冻结：

1. 兼容引擎、卡脚本、cards.cdb、协议和客户端的确切分支/commit/hash；DSH 插件及 provider 版本。
2. 模型层数/宽度/参数量、动作/构筑编码、损失权重、优化器与 PPO 超参数、LoRA 目标层和秩。
3. 三期具体牌表、对手池比例、晋级阈值、2026 卡池截止日、辅助对手实现。
4. 机型、并发、batch、吞吐、CPU 供给及预算细调；不从 A10/V100 名称直接承诺速度。
5. 预测胜率的校准、百场/千场统计口径；正式验收置信区间和容差规则。
6. PC 导出/量化/推理后端与 UI 技术栈；以资源和质量实测选择，不锁定旧 Flutter/Android 建议。
7. 发行前逐项审查所用代码、模型、卡图/文本与数据许可；代码开源不等于素材授权。

这些是工程参数和验证事项，不应重新打开已确认的角色划分、课程方向、LoRA 常规路线或移动端暂缓决定。当前不采用 DeepInfer；不把推理基础设施宣传为可直接提升本模型推理能力的训练算法。

## 18. 2026-10-24 用户确认：构筑逻辑与入口分类

本节补充并优先于前文尚未细化的构筑顺序；原目标/优化职责、硬约束和规则验证继续有效。

1. 第一阶段命名为**构筑逻辑**：效果类型、字段、种族等信息标签化，功能标签为轻量积木；图节点不先绑定具体卡 ID。粗连接件与标签独立，用通常召唤 `ns`、特殊召唤 `ss`、送墓时发动等宽泛描述，不塞详细卡文或创造复杂条件语言。允许分支、合流、替代路径。
2. 仅用户要求归属于狭义主题时，第二阶段按字段/种族筛主轴；广义主题跳过第二步直接第三步，仍保留第一步。主题例子不是硬性枚举。主轴候选不封闭通用卡或后续缺口召回。
3. 第三阶段读取具体卡文填卡和数量，复用已有评分/合法性/实际支持的引擎目标接口；粗逻辑不等于合法 CB，未支持和未验明确保留。
4. 构筑逻辑可按需求、填卡、决斗与各模型反馈持续调整、必要时重构；目标→优化循环保留，不能静默改变用户目标。
5. 不新增大模型。目标角色提候选逻辑，优化角色保目标改进，统筹安排阶段和汇总反馈；缺权重明确工程实现/未训练，不以规则模板冒充模型能力。
6. 入口采用可扩领域词典辅助的轻量非 LLM 文本分类器。按真实主轴意图识别狭义/广义；否定、别名、外挂、组合和未见主题需测试，低置信/混合歧义不得硬二选一。
7. 基本标签身份与注释元数据分开，只有联合标签展示使用 `·`。
