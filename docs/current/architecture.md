# 总体设计

版本：2026-11-11。与本目录的流程、评分、接口及训练正文共同构成现行设计。

## 目标与产品范围

项目自行训练决斗、构筑目标、构筑优化三个执行模型，由轻量统筹模型及确定性控制程序组织。目标是从用户主题、CB 或终场要求出发，理解真实卡效、形成合理构筑、推导基础路线、执行对局并从反馈学习，逐步迁移到陌生卡组。珠泪是复杂且具有随机性的起步课程，不能成为永久能力边界。单轴、双轴、复杂混轴按能力递进，始终允许纯轴或更简单的更优方案。

核心包含构筑、展开推理、对墙练习、来自有效牌组与驾驶策略的随机对抗、局内决策、复盘、自训练与持续适配。先交付完整可调用核心，再进行 PC 应用和 YGOPro／萌卡互操作；移动端和 YGOMobile 暂移出本期，未来有测试设备后另行恢复。联机能力、MD 屏幕接入和外部 AI 为独立扩展，不阻塞本地核心。体积压缩在核心可用后处理，旧移动端体积愿景不是开发门槛。

发行版实际对局与随机对抗在本地完成，外部 API 用于构筑辅助、检索、评价和复盘；开发训练中的 API 对手另行隔离记录。LLM 不作为基础模型组必需依赖。LoRA 则是形成基模后的常规持续适配路线，不能与可选 LLM 混为一谈。

## 模型职责

| 角色 | 职责及边界 |
| --- | --- |
| duel | 在引擎合法动作中快速选择，维护公开历史、计划、资源、妥协及恢复能力；实时内循环不逐动作往返统筹或 LLM。 |
| build_goal | 接收用户任务的结构化输入，对效果积木图和可选主题排序，交付无具体卡片的积木草案。基础 CB 阶段可排序路线目标。 |
| build_optimizer | 按积木草案的配套需求和实际卡文选卡，完善配套和投入数量，补齐主卡组、额外卡组和副牌，多轮比较修订。接收统筹、决斗及可选外部 AI 反馈。 |
| coordinator | 负责阶段调度、预算与结果交接。入口保存原文并把任务编码后交给目标模型。统筹网络提供调度建议，确定性程序负责权限、状态、合法性、版本、超时和异常。 |

三个执行模型独立训练编码器和权重，共享数据及接口规范，不强制共享可训练权重或全组端到端联合训练。首版以轻量 Transformer 和小型可学习调度器为方向，实际层数与参数由实测确定；短/长推理表示搜索、候选与迭代预算，不表示解释文字长度。程序产生候选、模型排序与真实参数更新分别记录。

目标模型交付效果积木草案后，优化模型持续选卡和修订，详见 [S0—S6](construction-workflow.md)。优化可换单卡或整轴，始终遵守卡片合法性、禁限、发行、数量和用户硬性要求，必要妥协须明确说明。

## 数据与效果表示

卡片表示分为基础属性、效果结构、情境关系。稳定卡片 ID 作为身份，别名、中日英名称和译名关联；中文效果、日文 FAQ／裁定及来源分别保存。三语能力覆盖名称消歧、跨语言对应、否定、费用/效果和次数限定，不要求每个来源提供三语完整卡文。向量相似不能替代身份映射，检索编码器不能替代裁定。

效果、主题、情境角色交叉检索；联合标签显示用“·”。功能积木与 ns、ss、送墓时发动等粗连接独立，允许分支、合流和替代。精确条件、费用、对象、区域、所有方、时点、次数和自肃由完整卡文及关系模块承接。原始事实、程序推断、模型判断、外部审核与人工修订分开。费用支付、效果处理、召唤手续和规则处理保留各自来源。

卡库、规则核心、效果脚本、禁限表、发行截止、标签、编码器和观察格式均有版本。禁表月份与发行截止分别固定，训练期间不自动加新卡。SQLite 管理身份、版本及实验索引，大批轨迹使用分片文件。未知、未读取和经审阅没有独立功能三者不能混用；完整文本已存在但未消费属于实现覆盖缺口。

识别模块可以提供更强的轴、泛用及联动认知；其接口读取卡文、实际投入、关系与有来源标签。构筑在该模块完善前仍须具备现有程序能够提供的基本配套判断，识别不足按能力结果报告，不新增整个构筑不可用的门槛。认知模块的后续设计和训练由用户独立推进。

必要废件、上限件、暂不可用、低收益和未知用途须在具体构筑中判断，不机械删除伴生卡。没有效果的怪兽也可能承担素材、调用对象或战斗功能；额外泛用是额外卡组泛用卡。用户参考牌表只用于独立评价和允许的分层提示，不能作为生成种子或直接装入 learner。对手牌表按其用途独立登记。萌卡只用于热门主题信息，不通过该渠道取得构筑。

## 决斗、搜索与时间控制

策略仅接收玩家合法可见信息：己方手牌、公开场面及公开历史。对手暗牌、牌序、未来抽牌、审计种子与完整调试状态隔离；未知可以推断，但必须与已知事实区别。搜索可能状态只从合法信息构造，外部 AI 对手遵守相同席位边界。

引擎提供合法动作和参数，模型选择发动、对象、素材、数量、顺序或通过。复杂响应逐步执行并保持上下文。基础 CB 仅作为有条件的计划，实际场面或对手响应变化后可调整，不强制重演预设动作。明确发动无效、效果无效、已付费用及不同次数限制对后续计划的影响。

先建立无搜索基线，关键分支按需搜索，比较质量与计算成本。搜索预算结束返回当前最佳合法动作；真实比赛超时由独立控制器终止任务、拒绝迟到动作、请求投降并确认结束，失败则保持终止状态并按协议关闭/重试，不能恢复出牌。释放底层 duel 不等于已向联机服务器投降。等待动画或无行动权时间不作为模型决策时间。

PC 决斗端到端目标为每动作约 1–3 秒，最终硬超时起点和阈值以产品测试确定；构筑上线目标 3–30 分钟，输出最佳已验证方案、验证范围及未满足项。开发/训练不套此上线时间限制，内部时间片自动续算。资源和时延按实际完整链路记录，不能用小矩阵或模型前向代替项目性能。

## 实现和交付原则

Python/PyTorch 为现行实现基础，复用真实规则生态，保留 CLI 与本地结构化服务。模型、数据、规则资源、训练入口、恢复和可复现交接构成软件阶段交付；GPU 吞吐、正式训练和能力验收属于训练阶段，PC GUI、量化、客户端互操作属于产品阶段。工具与运行版本以仓库资源锁和真实记录为准。

按模型布局、词表、规则资源、数据、游标和运行状态判断恢复兼容性；无关文件或换行变化不能强制重迁移。保留有效权重、优化器、RNG、累计更新与历史结果。未完成局和未确认事务不计正式成绩，不假定已经更新参数。

用户继续亲手完成适合入门的 Python 查询、过滤、统计和测试；辅助方提供拆解、讲解、骨架与审查。学习材料和有来源的第三方参考仍保留；旧设计正文由 Git 历史追溯。依赖许可及素材分发在上线阶段核对，不丢失来源记录。

## 决斗可用性与搜索状态

规则上的可发动、决策上的当前/后续可用，以及构筑分布中的废件统计是不同判断。可用也可能应保留；半废件须有可说明的补条件路径；限定范围内无用途需要已覆盖的排除依据；预算未覆盖或语义未知保留不确定。低优先级不等于废件。卡片结论聚合各效果、素材、费用及回收用途，随新事件和区域变化更新。

规划遵循合法性→费用/对象选择→连锁响应→实际结算→诱发新窗口。被干扰后按真实结果重建后续，不退回已付费用或继续使用预期产物。费用、素材与目标选择同计划联合考虑，不能由无关局部贪心破坏路线。

搜索去重保留影响未来的实体区域、剩余次数、限制、阶段、连锁及相关历史；画面相同不表示状态相同，图上有环也不表示无限资源。真实引擎快照或确定性重放不能由简化标签图替代。隐藏状态假设须与公开历史一致，汇总后只输出一个可见信息下可执行的动作，不把各未知世界分别最优的结果拼成现实策略。

即时展开、补条件、资源转换、保留干扰和延迟收益应获得可比较的搜索覆盖；记录扩展量、有效深度、未支持机制与覆盖缺口。实际响应资源与假定对手干扰压力场景分开；干扰类型、时点、成本分别保留。回退只能提交当时合法的选择，不能固定发送pass。解释来自实际日志、拒绝原因和验证范围。
