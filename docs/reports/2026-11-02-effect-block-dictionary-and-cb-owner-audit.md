## 1. 已有能力与“词典”的区别

| 当前实现 | 实际能力 | 不能据此声称的能力 |
|---|---|---|
| `LogicTag`、入口主题词典 | `dimension + value` 标签身份、主题与别名识别 | 不是通用卡效词典；入口能认出主题不代表理解卡文 |
| [effect_mechanisms.py](../../src/ygo_kito/effect_mechanisms.py) | `public-effect-clauses-v2`，用有限中文句式识别触发、费用、对象、操作、次数、自肃和部分素材 | 不是完整卡文解释器；未识别内容继续 unknown |
| [effect_records.py](../../src/ygo_kito/effect_records.py) | `public-effect-records-v1`，保留卡文及来源摘要、效果索引、资源变化、条件和未知项 | 有记录不等于记录全部正确、完整，也不等于每项已进入模型特征 |
| [construction_effect_blocks.py](../../src/ygo_kito/construction_effect_blocks.py) | 默认将上述识别投影为“卡组送墓”“墓地融合”两个粗功能标签；显式外部评审另外标来源 | 不能把两个自动标签的来源核对理解成通用效果词典验收 |
| [rule_references.py](../../src/ygo_kito/rule_references.py) | 局部次数及无效处理参考，绑定来源和适用范围 | 不是完整裁定库，参考记录本身不判定具体动作合法 |
| `BuildEncoder`、两层关系适配 | 构筑编码消费 18 维机制摘要，关系适配读取按效果记录；完整记录和定宽摘要分别存在 | 存在输入接口不证明模型学会语义；历史优化模型零更新另有核验 |

这套底座能够支持范围内的候选召回和关系判断，值得保留。主要缺口是规范功能词条和实际卡文的覆盖、限定条件的完整性，以及跨主题的语义正确性验证。现有有限句式和工程回归不能直接升级为“可靠通用词典已经完成”。

## 3. 基础 CB 的实际调用归属

静态调用链如下，核查时没有执行这些入口：

```text
AutonomousConstructionKernel.run_selected
  → ConstructionController.run
  → construction_fill.construction_cycle
  → basic_cb_provider
  → basic_cb_inference.infer_basic_cb
      → proposals：程序根据效果及素材生成路线目标
      → builder.models['build_goal']：排序候选目标
      → verify_goal → verify_combined / discover_goal
      → route_search：搜索原生引擎提供的合法动作
```

[infer_basic_cb](../../src/ygo_kito/basic_cb_inference.py) 明确读取 `builder.models['build_goal']`，输出标记为 `existing_goal_model_search_order_uncalibrated_not_quality`。模型只影响候选搜索次序，不生成完整动作链；符号提议范围主要是融合、同调和超量。

[route_search](../../src/ygo_kito/route_search.py) 的驱动为 `bounded-public-dto-route-search-v1`，对手使用中性通过策略。该入口没有决斗模型动作策略参数，也不读取 `build_optimizer`。因此准确归属是“目标模型参与目标排序，程序负责实际路线搜索，原生引擎验证”，不能写成已训练目标模型自主掌握 CB，更不能写成决斗模型在此负责推理。

原统一设计把组合及可执行路线提议列在目标模型职责内，现有接线与这一角色方向一致。本轮的新指令重新分配构筑层次，并未要求更换 CB 主责模型；新设计文档保留这一归属说明。

## 4. 与新流程仍有的差距

[construction_cycle](../../src/ygo_kito/construction_fill.py) 当前仍使用 `build_goal / build_optimizer / build_goal / build_optimizer` 的固定四角色序列。完成四次具体牌表交接后即进入 CB provider；这不等于“第一层目标模型、第二层优化模型持续迭代直至达标”。新设计尚未实施，不能因本文记录而把旧流程视作已替换。

现有条件 CB 固定明确起手，搜索使用种子 7 保持效果随机性和剩余牌序可复现。`proposals` 的起动卡筛选包含 `mill` 与 `send_grave`，没有以“后续不依赖随机结果”为统一准入条件。已有回执也注明效果随机性未穷尽检查。因此它仍可能找到依赖某次随机堆墓的路线，不满足本轮“线性、排除动态及随机不确定情形”的基础 CB 定义。固定起手与固定随机种子都不能替代这一排除检查。

同日用户进一步确认：基础 CB 可以包含固定随机堆墓动作，只是不推理命中后的分支，并须区分 cost 堆墓和效果堆墓。上段差距据此准确理解为“搜索可能消费命中内容继续展开”，而不是“出现随机堆墓动作就不属于基础 CB”。最新定义见[分工设计第5节](../plans/2026-11-02-construction-role-reassignment.md#5-基础-cb-的范围)。
