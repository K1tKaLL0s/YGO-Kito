# 两层评价的库存配套缺口修复

> 执行与历史记录。现行行为以 [现行设计](../../current/README.md) 为准；本文的日期状态和当时授权不自动适用于新任务。

用户要求：先查清两层为何漏掉实际配套缺口，再修复并按2207从空牌组重跑；禁止开始CB推理，不手工调整牌表，训练继续暂停。本轮由主进程执行，无子代理。此约束覆盖本轮测试和重跑，不能把“全流程”理解为恢复CB或训练授权。

## 原因与原运行证据

原始产物和四阶段记录见[此前运行报告](../2026-11-01-2207-construction-flow.md)。不是卡文缺失：资源中已有红玉之宝札的7星真红眼支付要求、弹匣的火山对象和卡雷多哈特的指名素材。遗漏发生在以下连接位置。

| 原位置 | 实际行为 | 造成的遗漏 |
| --- | --- | --- |
| `ConstructionLayerAdapter._automatic_context` | 仅当原任务`goal.card_id`固定某目标时，才将其素材需求作为用途接入 | `deck_constraints`任务已选额外的素材未进入有效比较 |
| `_record_facts`与自动条件占位 | 支付、对象记录有原文，但自动路径没有从选择条件匹配实际库存，并给未供给的条件插入unknown占位 | 不能区分“已知没有真红眼/火山组件”和“运行时能否取得仍未知” |
| 自动RoleAssessment及FunctionEvidence | 标签匹配即给功能covered，K/E统计没有扣除已知缺件的功能投入 | 缺配套卡仍能凭送墓等标签获得有效投入 |
| `compare_layer_candidates` | 必需比较受到全局unknown列表拦截 | 无关未知可以挡住局部可确认的库存改进 |
| 原portfolio | 生成器没有收到这类缺口的定向补件/替换提案 | 单靠重排不能保证出现修复候选 |

## 执行书与实现边界

目标是使有来源的必要组件缺口可见，并参与实际生成和选择。无CB动作、起手、连锁或局面搜索；不改变任务、模型特征、权重、checkpoint绑定、参考牌表、时期资源或引擎。

| 步骤／文件 | 前置与动作 | 不变量／验收 | 失败处理 |
| --- | --- | --- | --- |
| `construction_inventory.py` | 复用MechanismCatalog.effect_records与已识别素材描述，对完整识别的简单选择条件匹配实际库存 | 不按卡ID/主题配方判断；Side不供给；数量和素材实体不重复占用；不认识的限定保留待补 | 未识别文本不猜测，预算未覆盖单列 |
| `construction_layer_flow.py` | 自动上下文逐候选附加必要库存依赖；缺件功能的evidence改为missing，重新计算K/E | q仍表示方向；库存存在不等于区域可达或效果可发动；显式宿主上下文保持原行为 | 原任务/牌表验证失败仍拒绝候选 |
| 比较规则 | 按同来源缺口向量比较，短缺量和受影响实卡数分开，不相乘合成分数 | 已知库存改进不会被无关unknown抹掉；必需用途优先级和同级损失仍保留 | 未覆盖依赖不据此认定缺口已清除 |
| `construction_candidates.py` | 在原portfolio增加依赖候选家族，来源为缺件召回或受影响组件替换 | 每步通过assets.accepts，原池与预算不变；跨Side调入用程序完成原子交换；通常每个起点最多6步、每步128次检查 | 找不到可减少缺口的合法改动便停止该提案链，不手改输出 |
| `construction_fill.py`、`build_pipeline.py`的候选入口 | 第二次实际运行证明缺少图作用范围会修补未选效果；以兼容的可选graph参数把本轮图传到portfolio和依赖生成器 | 生成与评价使用同一功能范围；不改变原任务、模型输入或候选预算；家族内先提交严格改进链末端，再提交前缀 | 匿名作用范围与小预算回归必须通过；不得通过增加预算或改牌表消除失败 |
| `autonomous_construction.py` | `run_selected(..., basic_cb_enabled=False)`不创建CB provider，结果记录disabled_by_host | 默认接口兼容；本轮显式false；CB及引擎调用均须为0 | 验证进程调用CB提案/推理或原生引擎即报错 |
| 回归与2207重跑 | 先明确CPU测试，再用课程006原权重从空牌组运行四次交接 | 四阶段连续、合法输出、来源/修订可查、参数与暂停文件不变 | 保存失败现场，修复具体错误；不改变约束绕过 |

选择条件仅接受已支持的完整语法，例如数量、名称/字段、等级、种族和类型的明确组合；“以上”“以外”等未支持组合不会被删掉限定后强行匹配。手卡/卡组来源只能由主卡提供可能库存；墓地/场上检查只给库存上界，不证明可达。素材匹配使用有限实体匹配，排除目标自身那一份和明确禁止作融合素材的卡，不执行召唤过程。

已选功能按具体效果与所需操作关联。某效果的可选定向送墓缺件，不会因此否认同效果另一项独立抽卡功能。未解析的召唤方式、替代条件和复杂卡文仍保留，不能把必要库存检查扩张为完整效果可用性证明。

## 本轮实现中发现的预算问题

首轮禁用CB重跑已自动处理三个原缺口，但还留下已被识别的额外配套缺口。检查发现缺口提案扫描可能把检查预算花在无关主卡替换上；随后将替换对象限为受影响组件，只有明确召回的支撑件可以进入其他分区。匿名回归覆盖“仅Extra有缺口时，无关Main候选不能耗尽其预算”。

第二次重跑确认剩余原因有两项：生成器原本评价全部效果，但两层只评价本轮选中功能，导致前者先修补本轮未选的其他效果；修复链按第一步到末步入池，固定portfolio预算可能只容纳早期前缀。补充接线将本轮图经fill、build_pipeline传到依赖生成器，并在依赖家族内部先提交严格改进链末端。步数、检查数、portfolio预算和最终分项比较规则保持不变；最终候选仍由模型与两层选择。追加匿名回归分别检查未选效果不触发修复，以及小预算保留多份缺件修复的末端。这些修复均未写入任何实际卡名或牌表。

## 验证与接续

静态测试使用`tests.test_construction_inventory`、`tests.test_construction_layer_flow`、`tests.test_construction_relations`、`tests.test_construction_layers`明确模块。WSL另运行关闭CB的内核测试、目录绑定与编辑记录测试。所有测试均不运行CB。

实际重跑入口保存在`.cache/inventory-dependency-fix-20261101/run_no_cb.py`。它在相同进程中执行针对性回归，恢复原状态，然后调用`run_selected(base=None, basic_cb_enabled=False)`。CB推理、CB提案生成和NativeNormalEngine构造均有调用即失败的检测。105项两层相关测试及15项针对性CPU回归通过，9文件AST和diff格式检查通过。

当前代码的run-03从空牌组完成四阶段，63份绑定候选、465对比较；原三项缺口自动处理。最终仍有破坏剑、护宝炮妖及人偶怪兽三类资源缺口，涉及五张实卡，已识别并排除相应功能投入；第3、4阶段选中每条6步修复链末端，固定预算没有清空全部缺口。没有把漏检修复记为构筑质量全项通过。结果、牌表、调用计数和暂停状态见[最终运行报告](../2026-11-01-2207-inventory-fixed.md)及[机器回执](../2026-11-01-2207-inventory-fixed.json)。
