## 实际周期和计数

宿主选择configs/group-runner-v1.json，默认后端关闭；JSON方法/角色/revision仍沿用已验白名单。配方max_updates在本workflow中指周期数，stages_per_worker是进程阶段片段预算；指标明确区分阶段提交与真实优化器更新。

| 完整阶段边界 | 模型/任务行为 | 默认两周期结果 |
| --- | --- | --- |
| step0 | 四模型初始化、优化器为空、adapters=null | 0次更新，不称已训练 |
| bootstrap→step1 | 两个构筑基模、真实终局决斗、合成统筹各一次实际更新；然后冻结基模并建立四角色LoRA | 4次基模更新 |
| 每周期build_goal | 目标适配实际更新、排序合法候选及核心条件路线验证 | 2次目标适配更新 |
| build_optimizer | 优化适配实际更新，原定目标→优化→目标→优化四步重验，保留硬目标与三部分卡表 | 2次优化适配更新 |
| duel_train | 当前策略/本周期构筑/新种子完成真实对局，单epoch PPO适配 | 2次决斗适配更新 |
| coordinator_train | 轻量统筹适配实际更新，明示合成监督/建议 | 2次统筹适配更新 |
| evaluate | 先注册版本预测/任务，再冻结四模型/优化器/全部RNG/游标，真实核心评估与结果回收 | 2场已提交冻结对局 |
| feedback | 规则结束当前评估片段，记录建议/分歧/重构队列，下一课程周期带入反馈及incumbent | 2次反馈，13个总阶段提交 |

因此一个规范运行是**12次实际参数更新＝4基模＋8适配**，3场训练终局（含bootstrap）＋2场冻结验证；step13不是13次参数更新。三个独立验收运行合计36次已确认物理优化器调用、9场已提交训练、6场已提交冻结评估。崩溃注入在评估阶段，此阶段不执行优化器；丢失评估是否终局未知，不加入已提交分母，不编造额外胜负。

基模每个角色在适配阶段哈希/无梯度保持，四角色独立权重与优化器；rank4/alpha8是继承的工程值，不是正式冻结选择。周期中的预测为pending、不是校准胜率。弱对手/少量重复种子不代表能力或LoRA迁移收益，实际结果只作工程证据。
