## 一 用户的具体需求

### 1 基础识别的对象

输入应包含卡片或卡片组合，以及它所在的构筑和适用条件。输出应反映这个单元的功能、联动关系和构筑角色，而不是只根据卡名、字段、投入数量或固定目录分类。

- 大轴与小轴描述机制组合的相对投入、功能组织与完整性。大轴不必是核心，小轴不必是支援，不能用一个通用卡数阈值代替认知。
- 泛用指在不同构筑中具备可利用的功能与兼容性，不是对所有卡组无条件适用。
- 联动泛用可以由多张卡共同构成。标签属于完成相关功能的组合，成员不能自动继承整个组合的标签。
- 基础实现沿用已有五维角色：较大机制组、较小机制组、策略核心、支援作用、泛用性。它们可以重叠，不应强行变成互斥三分类。
- 要能识别完整组合、缺少必要成员、可替代成员、发动或使用条件改变、与构筑冲突等情况。应区别未知、证据不足和明确不兼容。

用户明确纠正：

> “伽马＋骨架作为组合才属于泛用”你是不是没有理解这个组合只是例子而不是全部

该例中“骨架”指组合中的驱动者。不能把“伽马＋驱动者”写成唯一联动泛用，也不能只增加几个手写组合后便宣称完成泛化。次元吸引者也只是条件变化的说明，不应变成另一个硬编码特例。

### 2 基础训练与 LoRA 的阶段顺序

用户最新明确：

> “LoRA 是用来根据对战反馈来微调对轴／泛用的认知的……后来出现了兼容这张卡或者可以接受这张卡负面作用的卡组，这张卡就变成了泛用，识别并学习这种变化才是引入 LoRA 的目标。”

正确顺序：

1. 先完成基础的功能、关系和构筑角色认知训练。
2. 通过必要的独立能力评估，保留实际失败和适用范围。
3. 之后依据真实对战反馈，学习环境、构筑兼容性和负面作用承受能力变化带来的认知更新，再使用 LoRA。

当前禁止自动执行“base 结束 → 用静态牌表再跑 LoRA”。历史静态 LoRA 产物只保留为工程与错误流程记录，不计入用户要求的实战反馈微调成果。历史不同时期的牌表也不能直接冒充已经验证的实战因果反馈。

### 1 示例过度特化和查询分布偏科

## 七 预期实现与建议接手顺序

以下是面向接手的实施建议，具体 API 和数据格式应复用现有工程，不要求另建一套框架。

### 第二步 集中修好基础输入与监督

- 输入保留成员功能、依赖、可替代关系、条件与冲突，以及所在构筑的上下文；不要只剩卡数或目录匹配结果。

- 从卡效与已有构筑关系构造候选，逐步降低对有限手写路线目录的依赖。没有可靠依据的标签保留未知。

- 训练采样关注角色与机制覆盖；评估另报告分组结果及真实数据分布表现。避免仅用总体分数掩盖稀疏家族失败。
